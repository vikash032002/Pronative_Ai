**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** Assumption: implementation should be concentrated in exact paths under the required layout, centered on `src/backend/OuterloopLabApi.sln`, `src/backend/Program.cs`, `src/backend/Controllers/ConversionsController.cs`, `src/backend/Services/CurrencyRateProvider.cs`, `src/backend/Services/ConversionAuditRepository.cs`, `src/backend/Models/ConversionRequest.cs`, `src/backend/Models/ConversionResult.cs`, `src/backend/Models/AuditTrailRecord.cs`, `src/frontend/index.html`, `src/frontend/src/main.tsx`, `src/frontend/src/App.tsx`, `src/frontend/src/api.ts`, and `src/frontend/entrypoint.sh`; if any of these files do not already exist, they should be created in those exact locations rather than moving the feature outside `src/backend` or `src/frontend`.

**In Scope:**
- Add a backend API endpoint at `POST /api/conversions` that accepts an amount, source currency, and target currency, fetches a live rate from the provider base URL configured by environment variable, normalizes the provider payload into an internal model, calculates the converted amount, and persists an audit record in Cosmos DB.
- Add backend retrieval endpoints for audit reconstruction: `GET /api/conversions/{id}` for exact-record lookup and `GET /api/conversions` with query filters for currency pair and date/time window so an analyst can locate a prior conversion without manual database inspection.
- Persist enough audit metadata to reconstruct a conversion exactly: request amount, source currency, target currency, normalized exchange rate, provider date/sequence marker if present, backend execution timestamp, and a stable record identifier returned to the frontend.
- Ensure startup prepares the required Cosmos DB database/container before serving requests, in line with the Known Constraints, so conversion persistence is available before the first API call succeeds.
- Add a frontend workflow in `src/frontend` that lets a user submit a conversion request, immediately view the converted amount and audit metadata, and retrieve prior conversions from a history/search view.

**Out of Scope:**
- User authentication, authorization, tenant management, or role-based access control beyond what already exists outside this feature.
- Scheduled rate ingestion, historical backfill, bulk import/export, or offline reconciliation jobs.
- PDF generation, spreadsheet export, email notifications, or auditor workflow tooling beyond on-screen retrieval of stored conversion records.
- Multi-provider routing, rate optimization, hedging, or any financial decisioning beyond a single live conversion request and its audit trail.

**Feature Constraints:**
- Use `IHttpClientFactory` for the external currency-rate call and keep all provider-specific request/response handling behind a single backend service so controllers and persistence code depend only on an internal normalized DTO.
- Use `decimal` for request amount, exchange rate, and converted amount; never use binary floating-point types for monetary calculations.
- Return a stable RFC 7807 `ProblemDetails` response with HTTP status `503` when the external provider cannot supply a usable rate; the response must not expose raw exception, network, or JSON parser details.
- Persist denormalized query fields needed for history lookup, at minimum the audit record id, source currency, target currency, provider date/sequence marker, and backend execution timestamp, so retrieval does not require recomputing values from the provider.
- The frontend should render stored audit values returned by the backend exactly as persisted for history/detail views; it must not recalculate converted amounts client-side after the initial API response.

**Expected Outcome:** When a user submits a request such as `amount=100.00`, `from=USD`, and `to=EUR`, and the normalized provider rate is `0.92` with provider date marker `2026-08-01`, `POST /api/conversions` returns `200 OK` with a new audit id plus values equivalent to `requestedAmount: 100.00`, `convertedAmount: 92.00`, `rate: 0.92`, `providerDateMarker: "2026-08-01"`, and a backend-generated `executedAtUtc` timestamp such as `2026-08-01T14:23:45.123Z`; the same values are written to Cosmos DB and are returned unchanged by `GET /api/conversions/{id}` and the frontend history/detail flow. If the provider call fails or returns an unusable payload, the API returns a `ProblemDetails` payload with status `503` and a stable title such as `Currency rate provider unavailable`, with no raw stack trace or serializer error text.
